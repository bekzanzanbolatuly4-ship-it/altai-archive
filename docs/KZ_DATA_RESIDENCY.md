# Казахстанское размещение персональных данных

## Текущее состояние

Подключённый Supabase-проект `altai-archive` размещён в `eu-central-1` (Франкфурт). Supabase не предлагает регион в Казахстане, а смена региона требует отдельного проекта и миграции. Vercel также не включает регион функций в Казахстане. Значит, одной смены адреса базы недостаточно: для казахстанского размещения нужно перенести серверное приложение, базу, аутентификацию, объектное хранилище и ограничители запросов.

До переноса не публиковать имена и отзывы посетителей и не заявлять о соответствии Production требованиям локализации данных. Эта записка — технический план, а не юридическое заключение.

## Кандидат на целевую инфраструктуру

Yandex Cloud Kazakhstan (`kz1`) — наиболее прямой из проверенных вариантов: официальная документация описывает Managed PostgreSQL, Managed Valkey, Object Storage, Compute Cloud, Kubernetes и Serverless Containers в казахстанском регионе. В текущей документации для региона указана одна зона доступности `kz1-a`; резервирование и аварийное восстановление нужно проектировать с учётом этого ограничения. До выбора провайдера владелец проекта должен проверить договор, список субподрядчиков, резервные копии, телеметрию, логи, поддержку и подходящие тарифы.

Рекомендуемая схема для сохранения текущего клиентского SDK — развернуть поддерживаемый self-hosted Supabase stack в Казахстане (Auth, Postgres, PostgREST, Storage и API gateway) и Next.js в том же регионе на управляемом контейнерном/VM-хостинге. Redis-ограничители заменить на локальный Managed Valkey либо другой подтверждённый ресурс `kz1`. Отдельно решить хранение административных файлов: `.data` на Vercel не является постоянным хранилищем; использовать приватный Object Storage в KZ с серверной авторизацией.

Self-hosted Supabase переносит ответственность за обновления, защиту, резервные копии, мониторинг и восстановление на оператора проекта. Перед выбором нужно проверить, поддерживает ли целевой хостинг и бюджет весь стек, а не только контейнер Next.js.

## Что покидает текущие системы

- Supabase Auth: email, учётные записи и хеши паролей.
- Supabase Database: профили посетителей, отзывы и административные таблицы.
- Upstash: лимиты и хешированные отпечатки IP/сообщений.
- Vercel: серверные функции, входящие HTTP-запросы и операционные логи.
- Gemini: пользовательский текст, если он передаётся для ответа или модерации. Не отправлять модели учётные данные и контакты; правила обработки и трансграничную передачу нужно согласовать отдельно.
- Локальный `.data`: административные записи и загруженные оригиналы, если они присутствуют в конкретном экземпляре проекта.

Перенос только Postgres оставит персональные данные в Auth, логах, ограничителе запросов или обработке функций за пределами KZ. Все потоки нужно проверить отдельно.

## План перехода без потери данных

1. Владелец создаёт и оплачивает целевой аккаунт/проект в выбранном KZ-провайдере; до этого ресурсы не создаются.
2. Утвердить владельца/оператора данных, цели и сроки хранения, контакты для запросов субъектов, трансграничную обработку AI и почты, резервирование и план реагирования.
3. Развернуть отдельную тестовую среду KZ. Поднять совместимый Auth/API/DB/Storage/Redis и Next.js; закрыть панели управления и БД от публичного доступа.
4. Снять проверенную резервную копию исходной базы и файлов. Переносить Auth только штатной процедурой для выбранного решения. Не копировать секреты и не раскрывать пользовательские записи в CI-логах.
5. Восстановить миграции и данные в тестовой среде, сверить количество записей, связи, политики доступа, подтверждение email, восстановление пароля, отзывы, загрузки и резервное восстановление.
6. Выполнить независимый security review и проверить юридические условия по фактическим местам хранения и обработки, включая журналы провайдера и AI.
7. Согласовать окно переключения: остановить записи, сделать финальную копию, сверить контрольные суммы/счётчики, переключить серверные URL и ключи, проверить сценарии, затем оставить исходный проект read-only на срок отката.
8. После стабилизации — отдельное решение владельца о сроке удаления исходных данных, резервных копий и секретов. Не удалять исходный проект автоматически.

## Что нужно для реального переноса

- Доступ владельца к аккаунту выбранного KZ-провайдера и утверждённый бюджет.
- Подтверждение оператора/контролёра данных и контакт для privacy-запросов.
- Договоры и подтверждённые регионы для hosting, backups, email/SMS и observability.
- Явное решение о Gemini: не отправлять пользовательские данные либо согласовать минимизированную трансграничную обработку.
- Окно переключения и ответственный за восстановление.

До получения этих условий допустимы только локальные изменения и тестовый план; Production данные не выгружаются и не копируются.
